# Amendment C — Finding provenance

**Status: consumed.** The analysis behind `concepts/finding-provenance`, which is now the live answer. Kept as the record of how the page was derived. Do not build from this file.

Amends Layer 1 (ontology), Layer 2 (lifecycles), Layer 3 (guardrails) and Layer 4 (seed). Written against the Mintlify docs repo at this revision.

---

## C1 · The gap, precisely

The product says **Findings**. The ontology says `rulecard_firing` — *"one evaluation of one rule card against one field."* Machine-generated by definition.

The literature confirms the gap is total. A search across the corpus returns nothing for a manually-raised finding. What exists is adjacent and deliberately weaker:

| What exists | What it is | Doc |
| --- | --- | --- |
| **New observation** | *"Log a ground-truth observation (photograph, note, sensor reading) at a map coordinate. Feeds `scout.completed` semantics."* | `guides/fields-workspace/overview.mdx` |
| **New note** | *"Free-form note attached to the Field or Block. **Not a task; not delivered as a notification.**"* | Same |
| **`scout.completed`** | Can `promote_severity`, `demote_severity` or `raise_contradiction` on a firing that already exists | `concepts/risk-model.mdx#activity-bindings` |

**The distinction the docs never draw is between an observation and a finding.** An observation is *evidence* — this is what I saw. A finding is a *judgement* — something is wrong here and it needs a decision. The platform accepts human evidence and permits it to move a machine judgement, but it does not permit a human to originate one.

**Humans can escalate. They cannot originate.** That is the gap in one sentence.

It matters most where the satellite is weakest. Rubber tapping-panel dryness *"shows as a slow, block-wide NDVI decline over 1–3 years"* (`guides/Crop/Rubber/rubber-ecosystems.mdx`); phosphorus and potassium deficiency are *"indirect only… requires soil test"* (`guides/crop-health-monitoring.mdx`). In exactly the cases where ground truth is the only reliable channel, the product has no way to record the conclusion.

## C2 · Shape — promote `finding`, do not add a sibling

Three options were considered.

**A · A discriminator on `rulecard_firing`.** Add `origin`, make `rulecard_id` nullable. Rejected: it forces five more nullable fields — `drivers`, `severity_score`, `yield_at_risk_pct`, `mitigation_window_days`, `rulecard_version` — and breaks the ID convention, since `firing_<scope>_<rulecard>_<date>` has no rulecard to name.

**B · A sibling entity, `manual_finding`.** Rejected on this project's own evidence. Every consumer — the queue, the map, the aggregation counts, the activity feed, the advisor — would read a union of two types. Duplicated authorities have produced **five separate defects** in this codebase already: the band table, `stage_today`, the crop names, the index vocabulary, the distortion words. A sixth is not worth the smaller diff.

**C · Promote `finding` to the entity. Recommended.**

`finding` becomes the concept. A rule-card firing becomes one way a finding arises.

```
finding
  origin: rulecard | manual
    rulecard  → carries everything rulecard_firing carries today
    manual    → carries author, rationale, attached evidence
```

**Why this is the honest model:** the UI has said *Findings* since Pass 2, and `FindingCard` is a design-system component. The product has been using the general word all along while the ontology carried only the narrow one. The drift is the tell — the UI was right.

**Cost, stated plainly.** This renames Layer 1 §1.10, Layer 2 §1.4, Layer 3 §1.3, and every reference in Layer 4's seed. It is a real refactor, not a field addition. It is worth it because every downstream consumer keeps reading one thing.

### IDs

| Origin | Pattern | Example |
| --- | --- | --- |
| `rulecard` | `finding_<scope>_<hazard>_<first_seen>` | `finding_muda_a2_rice_blast_20260612` |
| `manual` | `finding_<scope>_<slug>_<raised>` | `finding_ldg_perak_r3_panel_dryness_20260610` |

The `firing_` prefix retires. The slug on a manual finding comes from its hazard label, not free text.

### Fields

Shared by both origins: `id`, `field_id`, `block_id?`, `crop_cycle_id`, `origin`, `hazard_label`, `severity_band`, `first_seen`, `state`, `summary`.

Only on `rulecard`: `rulecard_id`, `rulecard_version`, `computed_band`, `severity_score`, `driver_evaluations`, `yield_at_risk_pct`, `estimated_loss_t`, `mitigation_window_days`, `yield_impact_layer_used`, `top_action_id`.

Only on `manual`: `raised_by` (FK → `user`), `rationale` (required), `evidence_refs[]` (photos, observations, soil results), `suggested_action?`, `review_state`.

**`hazard_label` is the field that keeps aggregation working.** `concepts/aggregation-model.mdx` rolls up *"alert counts by severity and category"* and `guides/national-overview.mdx` reports *"top national hazards"* keyed on rule card. A manual finding has no rule card, so without a hazard label it can only ever aggregate as "other". Where a manual finding names a hazard the literature already covers — panel dryness, phosphorus deficiency — it should carry that label so it rolls up beside its machine equivalents.

## C3 · Lifecycle

`rulecard_firing` runs `dormant → active → frozen → resolved | dismissed`. A manual finding is **never dormant** — nothing fires it; a person writes it.

| State | Manual finding |
| --- | --- |
| `dormant` | **Does not apply.** No `alert_bindings` to promote it |
| `active` | Entered on creation |
| `frozen` | Applies. A contradicting field check freezes it exactly as it does a machine finding |
| `resolved` | Applies, per **[L2D-1]**. The signal-based trigger cannot fire — there is no band to recompute — so resolution is explicit, by an agronomist, with a reason |
| `dismissed` | Applies, per **[L2D-2]**, with one difference below |

**Dismissal differs.** For a machine finding, dismissal suppresses re-firing of the same card on the same field and cycle for fourteen days, because the card would otherwise fire again. Nothing re-fires a manual finding, so its suppression window is meaningless. Dismissing a manual finding closes it outright, and the author is told — a manual finding dismissed silently is a person ignored silently.

## C4 · Severity — the hard question

**Can a human assign a severity that trips the safety floor?**

The floor is absolute: *"Severity ≥ high signals cannot be suppressed, muted beyond the bounded window declared below, or personalized away"* (`guides/semai-advisor/overview.mdx`).

Both plain answers are wrong. If any user can create an unsuppressible signal, attention becomes a denial-of-service surface and an internal political weapon. If a trained agronomist standing in a field cannot mark what they have seen as urgent, ground truth is second-class — which contradicts the entire scout loop, where a human observation is already permitted to escalate a machine finding to critical.

**Resolution: gate by role and rationale, not by origin.**

1. A manual finding may carry **any** severity band.
2. Severity **≥ high** requires a role that can hold responsibility for it — agronomist, manager or admin. A viewer may raise a finding at `watch` or below, or raise it unrated for triage.
3. Severity ≥ high requires a **non-empty rationale**. The floor's justification is that the signal is trustworthy; an unexplained urgent claim is not.
4. Every manual severity assignment is audited with actor, role at the time, rationale and timestamp, per the audit envelope.

**And the existing refusal must widen.** `guides/field-scouting.mdx` currently refuses *"suppressing a task that originates from a severity ≥ high **rule card**"*. As worded, a manual finding at high severity falls outside the floor — so human findings would be suppressible while machine ones are not, which is backwards. It should read **"a severity ≥ high finding, whatever its origin."**

## C5 · Guardrails

No new category. Extending the Field Scouting and Risk registers:

| Category | Rule |
| --- | --- |
| **Input validation** | A manual finding requires `field_id`, `hazard_label`, `summary` and `raised_by`. Rationale required when severity ≥ high. Evidence refs must resolve. |
| **Preconditions** | The field must have an active crop cycle — the same precondition a scout task already carries. |
| **Refusals** | Raising a finding on a closed cycle. Assigning severity ≥ high from a role that cannot hold it. Suppressing any severity ≥ high finding, whatever its origin. |
| **Confirmations** | Raising at severity ≥ high — cross-scope, since it reaches everyone routed to that band. Dismissing another person's manual finding. |
| **Soft warnings** | A manual finding duplicating an open machine finding on the same field and hazard. More than three manual findings raised on one field in seven days. |
| **Audit** | Actor, role at the time, rationale, severity, evidence refs, and any later severity change with its reason. |
| **Escalation** | A manual finding at severity ≥ high unacknowledged within its window escalates to the estate manager, as a machine finding does. |

## C6 · Downstream — three real limitations

**No `activity_bindings`.** Bindings are declared *on rule cards*. A manual finding has none, so a scout completion cannot automatically promote, demote or reset it. Severity change on a manual finding is a human act, audited. This is a genuine asymmetry and should be stated in the product rather than hidden: a machine finding responds to new evidence on its own; a manual one waits for its author.

**Not a verification source event.** `concepts/verification-model.mdx` anchors verification to *operations* — `scout.completed`, `map.applied`, `harvest.declared`. A finding is a judgement, not an operation. The **work it causes** is verifiable; the finding itself is not.

**Aggregation counts it, hazard rollups may not.** It counts in *"alerts by severity"* and in area affected. It appears in *"top hazards"* only where its `hazard_label` matches a known hazard. Findings with novel labels aggregate as "other" and should say so rather than being dropped.

## C7 · Disclosure

Every surface showing a finding can state where it came from.

- **Machine** is the default and carries no label in Product mode — labelling the common case adds noise. Review mode shows the rule card and version, as now.
- **Manual** always carries its author and date: *"Raised by Ali Ismail · 12 Jun"*.
- Where a manual finding sits beside machine findings in a queue, provenance is visible without opening it.
- A manual finding whose severity was later changed by someone else shows both — *"raised by Ali at watch · raised to high by Siti, 13 Jun"*.

State the rule; the design is not this document's business.

## C8 · Seed

One manual finding, chosen so it demonstrates *why the channel exists* rather than merely that it exists.

> **`finding_ldg_perak_r3_panel_dryness_20260610`** — Rubber, Ladang Perak Hulu. Raised by an agronomist at `high`. Hazard label `tapping_panel_dryness`. Rationale: bark inspection on Panel B shows dryness over roughly a fifth of the tapped length.
>
> **The satellite has not flagged it, and correctly so.** The literature states panel dryness *"shows as a slow, block-wide NDVI decline over 1–3 years, not a sharp drop"* and that NDRE picks it up earlier than NDVI. R3's readings are inside band. A machine-only platform sees nothing here for another year.

That single row makes the argument: the human channel is not a fallback for when the model is wrong, it is the channel for what the instrument cannot see.

Add a second, weaker case — a manual finding on `field_muda_b1` that **duplicates an open machine finding**, so the soft warning is reachable and the deduplication question is visible.

## C9 · Open questions

1. Can a manual finding be promoted into a rule-card **proposal** when the same hazard is raised repeatedly across fields? The advisor's Proposal artifact exists for knowledge gaps and this looks like one.
2. Does a manual finding contribute to the `farm_history` layer that calibrates future yield-impact resolution, or is that machine-observation only?
3. Should two manual findings on the same field and hazard be merged, and by whom?
4. What happens to an open manual finding when its crop cycle closes? A machine finding stops firing; a manual one has no such mechanism.
5. Should a manual finding expire if never acted on, and does expiry differ by severity?
6. Can an agency officer — read-only by role — raise a finding on a field they can see but do not operate?

## C10 · Docs delta

**The ontology is narrower than the product.** The UI, the design system's `FindingCard`, and every screen have said *Findings* since Pass 2, while Layer 1 carried only `rulecard_firing`. The general word was in use before the general entity existed.

**The safety-floor refusal is scoped to rule cards.** `guides/field-scouting.mdx` refuses suppressing *"a task that originates from a severity ≥ high rule card"*. Manual findings fall outside it as written. Widen to "whatever its origin".

**`New observation` has an undefined completion path.** `guides/fields-workspace/overview.mdx` says it *"feeds `scout.completed` semantics"*, but the FAB can raise one with no scout task open to complete. What `scout.completed` means with no task is unstated — and it is the closest thing the docs have to a human-originated signal.

**The alert/notification split has no home for this.** `guides/activity-and-alerts.mdx` divides the feed by source: alerts come from *data*, notifications come from *humans*. A human-raised field-level finding is field-critical like an alert and human-sourced like a notification. The taxonomy has no slot for it.

**Ground-truth-only hazards have no route into the product.** Phosphorus and potassium are *"indirect only… requires soil test"*; specific ion species are *"No — multispectral cannot separate ion species"*. The literature documents these hazards in full and the platform cannot record a conclusion about any of them.
